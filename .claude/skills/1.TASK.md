## Sumber kebenaran

Gunakan urutan otoritas dari `CLAUDE.md`:

1. Instruksi terbaru pengguna.
2. PRD v1.2.
3. User Story v1.2.
4. API Contract v1.1.
5. Database Schema v1.1.
6. Sequence Diagram v1.1.
7. System Design v1.0.
8. Ringkasan `.claude/specs/`.
9. Kode dan test yang sudah ada.

Jangan mengubah kontrak atau business rule untuk menyelesaikan checklist. Catat konflik dan
minta keputusan jika sumber berotoritas tinggi tidak cukup menentukan hasil.

## Cara memakai task pack

1. Baca `CLAUDE.md` dan task aktif secara lengkap.
2. Baca prompt yang dirujuk task; prompt adalah instruksi eksekusi, task adalah rencana/gate.
3. Baca skill area:
   - Backend: `hris-backend/SKILL.md`.
   - Frontend: `hris-frontend/SKILL.md`.
   - Git/review: `hris-git/SKILL.md`.
4. Verifikasi dependency dan gate task sebelumnya.
5. Pilih milestone/checklist pertama yang belum selesai.
6. Nyatakan scope, non-scope, branch yang diusulkan, file target, dan verification plan.
7. Implementasikan vertical slice terkecil yang lengkap.
8. Jalankan quality gate dan simpan evidence.
9. Centang hanya item yang benar-benar selesai dan terverifikasi.
10. Commit/push/PR hanya jika tindakan tersebut diotorisasi.

## Strategi fase

Gunakan contract-first dengan frontend mock yang mengikuti kontrak:

```text
Fase 0 — Foundation dan keputusan stack
  -> monorepo, Docker, config, backend/frontend skeleton
  -> Gate F0: semua skeleton build dan topology tervalidasi

Fase A — Kontrak
  -> OpenAPI 42 endpoint + schema/error/security
  -> Gate A: OpenAPI tervalidasi dan menjadi acuan kedua track

Fase B — Vertical slices
  -> Auth/RBAC
  -> Employee/Profile/Dashboard
  -> Attendance
  -> Leave/Overtime Approval
  -> Notification/Access/Audit
  -> Gate B: tiap slice lulus contract, role, integration, dan UI states

Fase C — Integrasi dan release readiness
  -> real API, E2E, security, accessibility, operability, release evidence
```

Backend dan frontend boleh berjalan paralel setelah kontrak operasi terkait stabil. Frontend
mock harus mengikuti OpenAPI; mock bukan sumber kontrak baru.

## Dependency graph

```text
Foundation + OpenAPI
        |
        v
Authentication + RBAC
        |
        v
Employee + Organization + Profile + Dashboard
        |
        +----------------------+
        |                      |
        v                      v
Attendance                Leave/Overtime Approval
        |                      |
        +-----------+----------+
                    v
        Notifications + Access + Audit
                    |
                    v
        Integration + Release Readiness
```

Important dependencies:

- Auth depends on `roles`, `users`, Redis, audit foundation, and approved token strategy.
- Employee depends on departments, positions, employee-user relation, storage adapter, and
  OpenAPI schemas.
- Attendance depends on employee identity, storage, camera/GPS frontend behavior, and worker.
- Approval depends on `employees.atasan_id`, leave/overtime schemas, atomic transitions, and
  worker escalation.
- Notifications depend on domain events from preceding modules.
- Integration depends on all contract operations and four synthetic role accounts.

## Ownership dan anti-konflik

| Concern | Primary owner | Other track |
|---|---|---|
| `backend/**` | Backend | Read-only except explicitly coordinated full-stack task |
| `frontend/**` | Frontend | Read-only except explicitly coordinated full-stack task |
| `docs/openapi.yaml` | Contract owner for active change | Consumers propose, do not silently diverge |
| Migrations/schema | Backend | Frontend reads contract projections |
| Frontend mocks | Frontend | Must mirror OpenAPI/backend behavior |
| `.claude/specs/**` | Coordinated documentation | Update only when source/decision changes |
| `CLAUDE.md` | Coordinated architecture guidance | Separate focused update where practical |
| Root Docker/Nginx | Foundation/integration owner | Coordinate before parallel edits |

Do not run parallel agents on overlapping files without an explicit merge/ownership plan.

## Gate antar-task

### Gate F0/A — Foundation and contract

- Repository structure and approved stack decisions are recorded.
- Docker topology validates; only Nginx is public.
- Backend API/worker and frontend skeleton build.
- PostgreSQL/Redis health behavior works.
- OpenAPI covers the approved 42 operations and validates without errors.

### Gate Auth

- Four roles are seeded and stable.
- Login/logout/lockout/session invalidation work.
- Frontend route initialization does not leak protected content.
- Negative authorization proves the backend is authoritative.

### Gate Employee

- Organization and employee schema/migrations are stable.
- HR CRUD, Top Management read-only, employee profile scope, storage, and exports work.
- Dashboard metrics use real approved data semantics.

### Gate Attendance and Approval

- Attendance invariants, file lifecycle, radius, and retention are verified.
- Approval routes, atomic decision, delegation, and escalation are verified.

### Gate Notification/Access

- Event-driven idempotent notifications and immutable audit behavior work.
- Permission administration matches the access matrix.

### Gate Release

- Contract-real API integration, E2E, negative authorization, security, accessibility,
  build/deployment, migrations, rollback, and known limitations are evidenced.

## Status

Use:

- `[ ]` — belum dikerjakan atau belum terverifikasi.
- `[x]` — selesai dan quality gate relevan lulus.
- `[!]` — blocked; tulis blocker, evidence, owner keputusan, dan next action.
- `[-]` — tidak berlaku setelah keputusan eksplisit; tulis alasan dan sumber keputusan.

Jangan centang task hanya karena file dibuat atau happy path berjalan. Jangan menyalin status
selesai dari proyek contoh.

## Alur sesi AI

Untuk setiap sesi:

1. Pilih satu milestone kecil.
2. Baca source of truth dan skill terkait.
3. Inspeksi repository/current changes sebelum membuat asumsi.
4. Pastikan foundation library yang diperlukan sudah disetujui.
5. Implementasikan contract + authorization + errors + tests + UI states bersama-sama.
6. Jalankan verification proporsional risiko.
7. Perbarui checklist dengan evidence singkat, bukan klaim umum.
8. Laporkan perubahan, command/result, assumption, blocker, dan remaining work.

## Definition of Done global

Sebuah task dianggap selesai bila:

- [ ] Semua acceptance criteria task terpenuhi.
- [ ] OpenAPI, schema, backend, frontend, mocks, dan docs sinkron.
- [ ] Positive dan negative authorization teruji.
- [ ] Migration/rollback/data impact aman dan terdokumentasi.
- [ ] Error states dan failure/cleanup behavior teruji.
- [ ] Tidak ada secret, PII nyata, debug artifact, atau unresolved critical check.
- [ ] Format, lint, test, build, contract, Docker, dan E2E relevan dilaporkan.
- [ ] UI responsif, keyboard accessible, dan Bahasa Indonesia.
- [ ] Observability dan audit sesuai risiko.
- [ ] Known limitations dan deferred scope jelas.
