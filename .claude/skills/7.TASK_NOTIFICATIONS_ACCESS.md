## Tujuan

Deliver recipient-scoped, idempotent in-app notifications; HR-managed and Top
Management-read-only role/permission views; immutable auditable security/business changes;
and cross-cutting hardening before full integration.

## In scope

- `notifications`, `permissions`, and `audit_logs` schema/migrations according to Database
  Schema v1.1.
- Notification list, unread count, mark read, dismiss.
- Events for request submission, transition, decision, delegation, escalation, contract H-30.
- Deterministic `event_key` and permanent per-event dismissal behavior.
- Role/permission list and HR permission update operation from API Contract.
- HR/Top Management audit log read/filter.
- Notification bell/list/deep link/read/dismiss frontend.
- Access and audit frontend with four-role guards/read-only behavior.
- Security, logging, rate-limit, integration, and contract hardening.

## Out of scope

- Public create-notification endpoint.
- Email, SMS, push, WhatsApp, or arbitrary templates.
- Recreating a dismissed event.
- Editing/deleting audit log.
- Top Management permission mutation.
- New role creation outside approved four-role scope unless explicitly defined by contract.
- Analytics modules not listed in current API Contract.

## Access mapping

| Area | Karyawan | Atasan | HR | Top Management |
|---|---|---|---|---|
| Notifications | Own only | Own only | Own only | Own only |
| Unread/read/dismiss | Own only | Own only | Own only | Own only |
| Role/permission view | No | No | Yes | Read-only |
| Permission mutation | No | No | Yes | No |
| Audit log | No | No | Read-only | Read-only |

All notification queries/mutations must include authenticated recipient scope.

## Notification event catalog

Define stable event names and deterministic keys for:

| Event | Recipient |
|---|---|
| Leave/overtime submitted | Active approver |
| Supervisor approved | HR and applicant as defined |
| Delegated to HR | HR and applicant/supervisor as defined |
| Auto-escalated | HR and applicant/supervisor as defined |
| Final approved/rejected | Applicant |
| Contract H-30 | Direct supervisor and HR |

Suggested conceptual key:

```text
<event_type>:<resource_id>:<stage_or_version>:<recipient_user_id>
```

Use the exact approved implementation format consistently. Event keys must distinguish
legitimate stages while deduplicating retries of the same event.

## Testing

### Notification

- Duplicate producer retry.
- Dismiss then producer retry remains hidden.
- Recipient A cannot list/read/dismiss recipient B.
- Unread count/list coherence.
- Safe deep link mapping.
- Durable event behavior on transaction/delivery failure.
- Contract reminder recipient and repeated-run cases.

### Access/audit

- HR read/update; Top Management read-only; Karyawan/Atasan forbidden.
- Permission update validation, audit, and cache invalidation.
- Negative mutation has no permission side effect.
- Audit INSERT succeeds; application UPDATE/DELETE fails.
- Audit filter/pagination and sensitive redaction.

### Frontend

- Bell/list count coherence and polling cleanup.
- Read/dismiss conflict/error recovery.
- Safe/unsafe deep link.
- Four-role route/action matrix and no-sensitive-fetch.
- Permission update confirmation/refetch.
- Audit responsive/accessibility states.

## Acceptance criteria

- [ ] Unique event key prevents duplicate notification.
- [ ] Dismiss uses `dismissed_at` and permanently suppresses the same event.
- [ ] Every notification operation is recipient-scoped.
- [ ] Approval and contract events cannot be silently lost on retry/failure.
- [ ] Contract H-30 reaches correct supervisor/HR recipients without incorrect self-notify.
- [ ] HR can administer approved permissions; Top Management is read-only.
- [ ] Karyawan/Atasan cannot access access/audit modules.
- [ ] Audit log is append-only in code and protected by DB privilege.
- [ ] Frontend count/list/deep-link/access state remains coherent and accessible.
- [ ] Cross-cutting hardening checks pass.

## Exit gate

Proceed to release integration only after idempotency/repeat-run, recipient isolation,
permission cache invalidation, immutable audit privilege, and security-log tests pass.
